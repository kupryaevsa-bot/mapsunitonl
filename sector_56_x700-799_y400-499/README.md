# Сектор №56 — x 700–799, y 400–499

Выгрузка всех элементов сектора, его JSON, скриншот и описание того, как тайлы сектора
собираются в карту. Сделано из `world_memory.json` тем же кодом, что рисует 2D-сборку
в приложении (`farm/export_assembly_region.py`, `static/js/assembly-view.js`).

---

## 1. Что это за сектор

- **Нумерация.** «№56» — 56-й сектор рабочего региона **12 × 13** (x 0–1199, y 0–1299),
  нумерация слева-направо, сверху-вниз: `55 = 4 × 12 + 7` → строка 4 (y = 400), столбец 7 (x = 700).
- **Квадрат:** x 700–799, y 400–499 = **100 × 100 игровых клеток** (≈ 200 × 200 м).
- **Тайлы:** 50 × 50 = **2500** тайлов земли; в памяти карты это `i` 800–996, `j` 1400–1596
  (мир: x = j/2, y = i/2).
- **Центр** для приложения: (750, 450).
- **В диагональном атласе** это кадр **№16 «Кирпичный квартал»**
  (`map_book/sectors/sector_x0700_y0400.jpg`, `Диагональ_24_сектора_рассказ.docx`).

## 3. Как тайлы складываются в карту (на примере этого сектора)

### 3.1 Откуда берутся данные

1. Фарм-боты пишут дампы (`.pcap/.pcapng/.json/.txt`), их разбирает `farm/dump_import.py`.
2. Из пакетов вытаскиваются две сущности:
   - **`sb` / `ub`** — блоки земли: `sb|mapW|mapH|i0|j0|h|w|packIdx|PACKED`.
     В `PACKED` на каждый тайл идут 2 символа, id = `(decode_char(a) << 6) | decode_char(b)`.
     `sb` — уровень 0, `ub` — уровень 1 (подземный слой, во Flash поднят на 85 px).
   - **`ol`** — объекты: `oid`, `i`, `j`, `level`, `depth`, `type`, список спрайтов
     `{ox, oy, pack, image, frames, hide}`.
3. Всё сливается в **`world_memory.json`** — единственный источник карты:
   сейчас в нём **750 000 тайлов** и **172 736 объектов** (`sb_ok` 2436, `ol_ok` 42883).

### 3.2 Сетка и координаты

- Клетка мира — `(i, j)`; **1 тайл = шаг 4 по i и j** (одна картинка закрывает 4×4 клетки).
- Игровые координаты: `x = j // 2`, `y = i // 2`. Значит шаг между тайлами — 2 по x/y.
- Сектор 100×100 клеток → **50×50 тайлов = 2500 записей**. В нашем секторе это
  `x = 700, 702, … 798` и `y = 400, 402, … 498`, то есть `i = 800…996`, `j = 1400…1596`.
- Каждый тайл — запись `{i, j, level, id}`; `id` — номер материала (см. 3.4).

### 3.3 Изометрия — главное правило сборки

Каждый тайл и объект ставится на экран по формулам:

```
sx = (i + j) * 16                      // 16 = HALF_W
sy = (i - j) * 8 - level * 85           // 8 = HALF_H, 85 = высота этажа
```

- Клетка на экране — ромб **32×16 px** (классическая изометрия 2:1).
- Рисунок тайла — **128×64 px** (4×4 клетки) и кладётся в точку `(sx - 32, sy - 32)`:
  левый верхний угол картинки, ромб при этом центрируется на клетке.
- Объект ставится в точку `(sx + ox, sy + oy)` — смещения `ox/oy` приходят из дампа.
- `level` поднимает всё вверх на `85` px за этаж (земля — 0, этажи 1–4).

Пример из сектора: тайл `(i, j) = (800, 1400)` → `sx = 35 200`, `sy = −4 800`,
картинка кладётся в `(35 168, −4 832)`.

### 3.5 Объекты

- Запись объекта: `{oid, i, j, level, depth, type, sprites[]}`.
- В секторе **1856 объектов** и **3890 спрайтов** (у 528 разных пар `pack/image`).
- По этажам: 0 — 1455, 1 — 220, 2 — 98, 3 — 68, 4 — 15.
- По числу спрайтов: 1 спрайт — 1567 объектов, 2 — 118, 3–5 — 104, 6–10 — 30,
  11–30 — 22, больше 30 — 15.
- Каждый спрайт: `pack` → папка, `image` → PNG `static/tiles/rp/{pack}/IMAGE_{image}.png`;
  `frames` — кадров в спрайте (рисуется первый), `hide` — служебный флаг
  (рисуются `hide = 0, 1, 3`; в секторе скрыт 1 спрайт с `hide = 2`).
- 89 разных паков. Топ: асфальт 4 (681), навесы и крыши 25 (372), обломки/щебень 63 (317),
  крыши 26 (250), фонари 24 (184), витрины/стенды 90 (168), навес/рынок 77 (129),

- Самый крупный объект всего `world_memory` — **oid 277657** (193 спрайта, x 753, y 489,
  level 1, паки 3/39/76/77/83) — стоит именно в этом секторе; рядом его части
  oid 19380 (180 спрайтов) и oid 289602/289603 (по 109).

### 3.6 Порядок отрисовки (почему всё не «схлопывается»)

1. **Тайлы** сортируются по `(level, i+j, i, j)` и рисуются от дальних к ближним:
   `i+j` — это «глубина» в изометрии, ближние тайлы перекрывают дальние.
2. **Объекты** сортируются по `(level, depth, oid)` — сначала нижние этажи и дальние,
   потом ближние и высокие; поэтому фасады домов закрывают то, что за ними.
3. Рисование идёт на один холст: сначала вся земля, потом все объекты.

Именно поэтому **свежий скриншот отличается от старой вырезки атласа**: в атласе
(`sector_crops.py`) объекты рисовались в порядке `oid` без сортировки по `depth`,
и там крыши/навесы местами лежат поверх фасадов. Свежий рендер сортирует объекты
правильно — так сектор выглядит в приложении.

### 3.7 Склейка конкретного сектора — по шагам

1. Из `world_memory.json` выбираются записи с `x = j/2` и `y = i/2` в пределах
   x 700–799, y 400–499 (допуск ±0,25 клетки): 2500 тайлов + 1856 объектов.
2. Вычисляется bounding box по всем тайлам и спрайтам: `35166…41937` по X и
   `−6400…−2911` по Y (≈ 6771×3489 px в масштабе 1:1).
3. Масштаб: `3600 / 6771 = 0,5317`; холст 3628×1883 px, плюс рамка → 3656×2015 px.
4. Тайлы рисуются на масштабе как ромбы 68×34 px, объекты — из своих PNG с учётом `ox/oy/level`.
5. Картинка сохраняется в PNG и JPEG, сверху шапка с координатами, снизу — легенда.
6. В приложении (`static/js/assembly-view.js`) те же формулы `gridToScreen`, `tileAt`,
   сортировки и пути к PNG — поэтому выгрузка и экран показывают одно и то же.

### 3.8 Состояние сборки по данным приложения

- Покрытие: **100 %**, клеток 2500 / 2500, дыр 0.
- Пропущенных PNG: 0.
- Вручную «готовым» сектор **не отмечен**; точек, где персонаж стоял, в секторе 0 —
  то есть по правилам приложения (100 % + стояние в центре) он пока не готов.
